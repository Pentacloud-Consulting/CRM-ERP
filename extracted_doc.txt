1. Introduction & Scope
This document specifies the CRM-to-ERP lead lifecycle and the air freight logistics data model, AI-assisted UI/UX, and system integration architecture for an AI-native Logistics and Air Freight management system. It builds directly on the shared CRM foundation defined in the base platform specification — Lead, Account, Contact, and Opportunity — and extends it into a full air freight operating model: booking, documentation, flight allocation, tracking, and customs clearance.
The specification is organized into three parts, matching the scope requested for engineering handoff:
CRM Lead Lifecycle — the standard lead-to-Opportunity conversion process, including the trigger logic and data persistence requirements fired by the “Convert” action.
Logistics & Air Freight Data Schema — end-to-end objects (Shipment, Booking Request, Air Waybill, Flight Manifest, ULD, Tracking/FSU, Customs Clearance) with field types and relational mapping, using IATA-standard terminology.
Technical UI/UX Specification and System Architecture & Integration Logic — AI-assisted data entry, dynamic tracking visualization, exception-handling UI patterns, and the backend event/message architecture that maps Cargo-IMP/XML traffic onto the schema.
As with the base platform, every table below carries the standard audit and multi-tenancy columns defined in §2.5, and every cross-domain hand-off is implemented as a published domain event rather than a direct cross-service database write.

2.3 Trigger Logic: The “Convert” Action
Clicking “Convert” on a Qualified lead is a single user-initiated command handled entirely inside the CRM service; it does not touch the ERP/logistics schema at this stage. The command executes as one atomic server-side transaction with the following steps, in order:
Eligibility check — the button is only enabled when Lead.status = ‘Qualified’; the server re-validates status at request time to guard against a stale UI state or a double-click.
Duplicate resolution — the Account table is searched by tax_id (if captured) and a fuzzy match on legal_name/country; if a probable match is found, the UI presents “Link to existing Account” as an alternative to creating a new one, rather than silently creating a duplicate.
Field mapping — the mapping table in §2.4 is applied to build the three new (or linked) records in memory: Account, Contact, Opportunity.
Atomic persistence — all writes (Account insert/update, Contact insert, Opportunity insert, Lead update) execute inside a single database transaction. If any write fails — e.g. a uniqueness constraint on Contact.email — the entire transaction rolls back and the Lead remains Qualified with no partial objects created.
Conversion lock — on commit, Lead.status is set to ‘Converted’ and Lead.converted_at is stamped in the same transaction. The Convert button becomes permanently disabled for that Lead the moment converted_at is non-null, making the operation idempotent — a retried or duplicate request is rejected before it reaches the write path.
Domain event — a LeadConverted event (lead_id, account_id, contact_id, opportunity_id, converted_by, converted_at) is published to the shared event bus after commit, for activity-feed, notification, and audit-log consumers; no consumer can block or fail the conversion itself, since the event fires only after the transaction has already succeeded.
UI redirect — the user is navigated directly to the new Opportunity record with the Account and Contact already linked in its header, so the rep can continue straight into quoting without re-entering data.

2.5 Data Persistence Requirements
Transactional scope: the four writes in §2.3 (Account, Contact, Opportunity, Lead) must share one database transaction with SERIALIZABLE or equivalent isolation on the Lead row, so two simultaneous Convert requests on the same Lead cannot both succeed.
Referential integrity: Contact.account_id and Opportunity.account_id / primary_contact_id are foreign keys populated within the same transaction that creates their targets — no eventually-consistent linkage for this hand-off, unlike the CRM→ERP boundary in §5.2, because all three objects live in the same CRM service and schema.
Audit trail: every field copied in §2.4 is written once at conversion time with normal audit columns (created_by, created_at); subsequent edits to the Opportunity do not retroactively change the Lead, which remains a frozen historical record.
Non-destructive Lead retention: the Lead row is never deleted on conversion (is_deleted stays FALSE); it is kept, status = Converted, as the permanent source-of-truth for lead-to-deal conversion-rate reporting.
Rollback safety: if the transaction fails at any step, no LeadConverted event is published — event publication is strictly post-commit, preventing downstream consumers from ever observing a conversion that didn’t actually happen.

Field and status terminology follows IATA Cargo-IMP / Cargo-XML and ONE Record conventions so the schema maps directly onto real EDI/API traffic (§6).

4.2 AI-Assisted Data Entry: Automated Document Extraction
Booking Requests and Air Waybills are frequently first specified by a shipper-provided commercial invoice, packing list, or DG declaration rather than typed in directly. The extraction flow reuses the same governed, human-in-the-loop pattern the base platform uses for natural-language queries (interpretation → confirmation → commit), applied here to document fields instead of SQL:
State
Trigger
System behavior
Uploaded
User drags a PDF/image (invoice, packing list, DG declaration) onto the AWB or Booking Request form.
Document is stored and queued for extraction; the form remains editable and unblocked.
Extracted (Proposed)
AI extraction model returns structured field values with a per-field confidence score.
Every extracted field is pre-filled but visually flagged (e.g. amber underline) until reviewed — low-confidence fields (weight, HS codes, declared value) are flagged more prominently than high-confidence ones (airport codes, dates).
Accepted
User reviews and clicks “Accept fields” (bulk) or edits individual values before saving.
Accepted values are written to the AWB/Booking Request row; the source document and every original extracted value are retained for audit, even where the user overrode them.
Escalated
Confidence on a required field (e.g. declared value for customs, DG UN number) falls below threshold.
That field is left blank rather than guessed, and the form blocks save on it specifically — mirroring the base platform’s rule that the AI layer must ask rather than guess (§3.2 of the technical specification).
Extraction never writes directly to the Air Waybill or Booking Request table — it only ever populates the pending form state a human then accepts, keeping the same separation between AI proposal and governed persistence used throughout the platform.
4.3 Dynamic Tracking Visualizations
Shipment map view — origin/destination airports plotted on a route map with the current position (last DEP/ARR event) highlighted; used on the Shipment detail panel and embeddable in the AI panel’s result card for “where is this shipment” questions.
Milestone timeline — a horizontal strip of FSU codes (RCS → DEP → ARR → RCF → NFD → CCD → DLV) with completed steps solid and the current step animated; hovering a step shows event_timestamp, location, and source.
Multi-leg / split-shipment rendering — where manifest_line_items shows an AWB spread across more than one flight leg or ULD allocations show a split across containers, the timeline branches to show each piece group’s progress independently rather than collapsing to a single misleading status.
Live updates — the timeline and map subscribe to the same tracking-event stream the backend ingests from FSU messages (§6.2); a new event updates the UI via websocket/polling without a page reload, consistent with the base platform’s event-driven UI pattern.
4.4 Exception Management UI Patterns
Air freight exceptions — customs holds, manifest discrepancies, DG mishandling, missed connections — are surfaced as a first-class Exception Queue rather than buried inside individual shipment records:
Exception Queue — a filterable list of every Shipment/AWB currently in status = Customs Hold or Exception, or with an AWR/MAN tracking event, sorted by SLA urgency (time since the triggering event) rather than creation date.
SLA countdown — each exception row shows a live countdown against the relevant SLA (e.g. hours since a customs hold began), color-shifting from neutral to amber to red as it approaches breach, so operations staff can triage without opening every record.
ULD build-up board — a drag-and-drop Kanban-style board (per ULD, per flight manifest) where warehouse staff assign AWB piece groups into ULDs; drops write directly to uld_allocations and update ULD.status, with weight/volume limits enforced client-side against tare/max_gross_weight before the drop is accepted.
Irregularity report (CIR) workflow — raising a Cargo Irregularity Report from an exception pre-fills shipment, AWB, and event context, routes it to the responsible station, and links the resulting record back onto the Shipment’s timeline as a visible flag — never a silent status change.
Customs hold detail — the Customs Clearance record’s hold_reason is shown directly on the Shipment detail panel with a “notify broker” action, rather than requiring navigation into a separate Customs module to understand why a shipment is stuck.
5. System Architecture & Integration Logic
The logistics service ingests industry-standard air cargo messaging — Cargo-IMP (Type B / EDIFACT-style) and Cargo-XML, including ONE Record REST resources where partners support it — normalizes it into the canonical event schema below, and bridges it to the CRM domain over the same shared event bus described in the base platform specification (§5.2 of the technical specification).

Every applied message retains a pointer from its resulting row(s) back to the raw payload (raw_message_ref on tracking events; equivalent references on AWB/manifest updates) for full message-to-record traceability.

5.4 API Layer & Technology Stack
A single API gateway continues to front CRM and logistics as independent services, composing cross-domain views (e.g. “Opportunity with its resulting Shipment and current tracking status”) rather than the services calling each other synchronously.
A dedicated EDI/message broker sits in front of the logistics service for Cargo-IMP (Type B network) and Cargo-XML/ONE Record traffic, decoupling carrier connectivity protocols from the internal event bus.
The AI query service remains a separate consumer of the gateway and the semantic layer, with no direct database credentials — only access to the governed query execution endpoint, unchanged from the base platform.
